## 問題別

### A・B・C
- **A**: 桁数を `to_s.size` で数えている。問題ありません。
- **B**（AC 15.1 分 / 不正解 1）: 線分ごとに `K` が両端の間（端を含む）にあれば数え、2 本で共有される端点の重複を引いています。正しいのですが、補正が `+1`（最後の点）と `-cnt` の 2 つに分かれています。公式は、端点を `A.count(K)` で、端点以外を `A[i] < K < A[i+1]` または `A[i] > K > A[i+1]` で数えます。2 つは重ならないので補正が要りません。
  - **不正解の原因**（WA 版のコードを本人から受け取って確認）: WA 版は `cnt += 1 if K == A[i - 1]` で、`A[0]`〜`A[N-2]` の側を数えていました。一方、補正の `ans += 1 if A[-1] == K` は最後の点の側を足しています。そのため、先頭の点が `K` だと 1 回も数えられず（1 - 1 = 0）、末尾の点が `K` だと 2 回数えられます（1 + 1 = 2）。`N K = 2 1`、`A = 1 2` では 0 を出します（正しくは 1）。サンプル 2（`3 1 3`）は両端がともに `K` なので誤差が打ち消し合い、サンプル 1 はどちらの端も `K` でないので、どちらのサンプルも通っていました。
  - 重複を引く補正は、足す側と引く側が同じ端を指しているかを確かめないと、こうしてずれる。公式のように「端点」と「端点以外」に分けて数えれば、補正そのものが要らない。前回（480）の B・C と同じく、場合分けの片側の処理がずれた WA。
- **C**: Hash で名前から ID を引いています。`cnt` の代わりに `accounts[name] ||= accounts.size + 1` と書けば、変数が 1 つ減ります。

### D - Autopilot（AC 27.2 分 / 不正解 0）
**アルゴリズム**: あなた: ダイクストラ法 / 公式: 01-BFS

隣接リストをソートし、先頭の辺だけコスト 0、残りをコスト 1 としています。辺のモデル化は公式と同じです。隣接リストのソートが全体で O(M log M) かかるので、01-BFS にしても全体のオーダーは変わりません。今の解法で十分です。

### E - Most Brilliant Starry Sky（着手・未 AC / 不正解 2）
**アルゴリズム**: 偏角ソート、外積・内積。あなた: 二分探索（反対側の境界を探す） / 公式: 尺取り法（円環を 2 倍に伸ばす）

**どこまで合っていたか**: 方針は正しいです。各星を半平面の始点にし、偏角が `[θ, θ+180°)` に入る星を数えます。補集合を `n - cnt` で同時に見ていて、計算量は O(N log N) です。直したコードを `N = 2×10^5` で手元計測すると約 0.5 秒でした（ジャッジでの値ではありません）。**考察は合っていて、偏角の比較の向きだけが違っていました。**

**原因（愚直解との突き合わせで確認済み）**
1. `zone[1]` と `zone[2]` の比較関数が `a[0] * b[1] <=> a[1] * b[0]` になっていて、偏角の**降順**に並んでいました。`zone[0]` と `zone[3]` は昇順です。
2. `zone[3]` と `zone[0]` を `bsearch_index` で探す条件が逆向きでした。「`-(x1, y1)` より偏角が小さい」になっていて、正しくは「大きい」です。

反例（6 点がすべて 180° 未満の幅に収まり、答えは 6 なのに 5 を出す）:
```
1
6
0 -1
-2 -3
3 -2
1 0
1 -3
2 2
```

**最小の直し方**は次の 4 行です。修正後は、小さい座標のランダム入力 1000 件で愚直解と一致しました。1 と 2 は片方だけ直しても落ちることも確かめています。
```ruby
  zone[1].sort! {|a, b| a[1] * b[0] <=> a[0] * b[1] }
  zone[2].sort! {|a, b| a[1] * b[0] <=> a[0] * b[1] }
  ...
    idx = zone[3].bsearch_index { it[1] * (-x1) > it[0] * (-y1) } || zone[3].size
  ...
    idx = zone[0].bsearch_index { it[1] * (-x1) > it[0] * (-y1) } || zone[0].size
```

**気づきたかったポイント**: 偏角の差が 180° 未満の 2 点なら、どの象限にあっても `cross(a, b) > 0` は「a が先」を意味します。外積の符号は x や y の正負で反転しません。なので 4 つの象限すべてで比較関数は 1 つで済み、二分探索の条件も 1 種類で済みます。象限ごとに不等号の向きを考え直したところで向きを取り違えたのだと思います（推定）。

**公式・別解との違い**
- 公式: 442 E と同じ半分割の比較で一度だけソートし、配列を 2 倍に伸ばして尺取り法で調べます。比較関数を 1 つ書くだけで済みます。
- ユーザ解説（snuke さん案）: 各星の反対側 `(-X, -Y)` に重み 0 の点を足して 2N 点をソートします。すると答えは「長さ N の連続区間に入る重み 1 の点の数の最大値」になり、尺取り法も要りません。
- あなたの方法も同じ O(N log N) ですが、同じ形のコードを 4 回書くので、向きを間違える箇所も 4 倍になります。

**1 回目の WA（56.5 分、atan2 版）の原因**（WA 版のコードを本人から受け取って確認）: `Math.atan2` で偏角を浮動小数点数にしてソートし、2 倍に伸ばした配列で `cur + Math::PI` を超える最初の位置を二分探索していました。**方針は公式と同じで、落ちた原因は浮動小数点数の誤差です。** 座標が 10^9 まであると、ほぼ反対向きの 2 点の偏角の差は 10^-18 程度まで小さくなります。double で表せる差は π の近くで 4×10^-16 程度なので、「ちょうど 180° の内か外か」を区別できません。公式解説も、atan2 は誤差で WA になりうると注意しています。

反例（`p` と `q` の外積が -1 で、`q` は `p` のちょうど反対向きからわずかに外れている。正しい答えは 2 で、atan2 版は 3 を出す）:
```
1
3
999999999 999999998
-1000000000 -999999999
-999999998 999999999
```
小さい座標のランダム入力 200 件では、atan2 版も愚直解と一致しました。考察は合っていて、誤差だけで落ちていたことになります。

**時間の使い方**: 1 回目の WA から 2 回目の WA までの約 42 分は、4 象限に分けた整数版への書き直しに使われています。誤差が原因だと気づいたのは正しい判断でした。ただ、そのときは atan2 版の形を残したまま、比較だけを `abc442/e` の `Point#<=>` に差し替えれば済みました。2 倍に伸ばした配列の `i` から `i + n` までは偏角が θ から θ+360° まで並ぶので、`cur.cross(q) < 0` は「θ+180° を超えた」を表し、途中で false から true に 1 回だけ変わります。二分探索の条件もそのまま整数に直せます。この版は、サンプル、上の反例、小さい座標 300 件と大きい座標 200 件のランダム入力で、愚直解と一致しました。最大入力の手元計測は 0.91 秒です（ジャッジの値ではありません）。
```ruby
gets.to_i.times do
  n = gets.to_i
  points = Array.new(n) { Point.new(*gets.split.map(&:to_i)) }.sort   # Point は abc442/e のもの
  points2 = points + points
  ans = 0
  n.times do |i|
    cur = points2[i]
    idx = (i + 1...i + n).bsearch { cur.cross(points2[it]) < 0 } || i + n
    ans = [ans, idx - i, n - (idx - i)].max
  end
  puts ans
end
```

**デバッグ**: 2 回目の WA（4 象限版）は、愚直解との突き合わせなら 12 回目の試行で反例が出ました。数秒で見つかる誤りです。愚直解は 5 行で書けます。
```ruby
gets.to_i.times do
  n = gets.to_i
  ps = Array.new(n) { gets.split.map(&:to_i) }
  puts ps.map { |sx, sy| c = ps.count { |x, y| (x == sx && y == sy) || sx * y - sy * x > 0 }; [c, n - c].max }.max
end
```
20 点のサンプルは、比較の半分が逆向きのコードでも通っていました。サンプルが通ることは、こうした符号の誤りがないことの裏づけになりません。

### F - Evil Shortest Path（未着手）
**アルゴリズム**: 公式: 変形ダイクストラ法

スコアは辺を通るたびに `10s + c` と増えるので、ダイクストラ法がそのまま成り立ちます。ただし、スコアは最大 N 桁になるので直接は比べられません。鍵になる観察は次のとおりです。
- 確定した頂点のスコアに小さい順の「順位」を付ける。
- 移動後のスコアの大小は、組 `(移動元の順位, 辺の数字)` の辞書順と一致する。`s < t` なら `10s + 9 < 10t + 1` だから。

優先度付きキューに入れる値をこの組に替え、`998244353` で割った余りは別に持ちます。D で書いたダイクストラ法から 1 段の言い換えで届く問題です。

## ヘッダー

C・D・E の `main.rb` に書き込み済み。

E は終了後に 4 象限版を直して AC した後、`abc442/e` の `Point#<=>` で一度だけソートし、2 周分並べた配列で尺取り法を使う形に書き直しました（ヘッダーは「偏角ソート」「尺取り法（円環を 2 周分並べる）」）。補集合の `n - cnt` は、すべての星を始点として調べているので不要で、外しています。

途中で二分探索の版も書きました。境界を探す部分は、二分探索だと合計 O(N log N)、尺取り法だと右端が戻らないので O(N) です。ただ、どちらもソートに O(N log N) かかるので、全体の計算量は同じです。最大入力での手元計測では、ソート 0.49 秒、二分探索 0.23 秒、尺取り 0.04 秒でした。

尺取り法に差し替えたとき、右端の上限を `r < 2 * n` にして WA になりました。全部の星が 180° 未満に収まると、`r` が `i + n`（始点と同じ星、外積 0）を越えて 2 周目まで数えてしまいます。上限を `r < i + n` にすれば直ります。2 周分の配列で尺取り法を使うときは、窓の長さが `n` を超えないように右端の上限を `i + n` にする（公式の実装例も `while r < l + n`）。

B は付けるなら「場合分け（端点とそれ以外を分けて数える）」です。
